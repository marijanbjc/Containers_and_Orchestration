# ЛР 1. Dockerfile

Приложение представляет собой зашедуленную таску, которая ходит в базы, выполняет выгрузки и преобразования данных и складывает их на диск.

## Структура репозитория

| Файл | Описание |
|---|---|
| `Dockerfile_bad` | Плохой Dockerfile: работает, но содержит плохие практики |
| `Dockerfile_good` | Хороший Dockerfile: плохие практики исправлены |

## Сборка и запуск

**Плохой образ:**

```bash
docker build -f Dockerfile_bad -t app_bad .
docker run -v app_data_bad:/src/data app_bad
```

**Хороший образ:**

```bash
docker build -f Dockerfile_good -t app_good .
docker run -v app_data:/home/appuser/src/data app_good
```


## Плохие практики в `Dockerfile_bad` и их исправление

### 1. Плавающий тег базового образа (`python:latest`)

**Как в плохом:**  
Не фиксируем версию базового образа. Из-за этого не обеспечивается воспроизводимость и идентичность контейнеров.

```dockerfile
FROM python:latest
```

**Как исправлено в хорошем:**

```dockerfile
FROM python:3.14-alpine
```


### 2. Копирование проекта до установки зависимостей (не работает кеш слоёв)

**Как в плохом:**  
Сначала создаётся слой с файлами проекта (которые меняются часто), а уже поверх него делается слой с зависимостями (которые меняются реже). Из-за этого при любом, даже минимальном, изменении кода в проекте, в образе заново будут резолвиться и устанавливаться все зависимости.

```dockerfile
COPY src .
...
RUN pip install --no-cache-dir -r requirements.txt
```

**Как исправлено в хорошем:**  
Сначала устанавливаем все зависимости и только затем создаём слой, в котором копируется постоянно меняющаяся кодовая база.

```dockerfile
COPY core_requirements.txt src/requirements.txt ./
RUN pip install --no-cache-dir -r core_requirements.txt && \
    pip install --no-cache-dir -r requirements.txt
...
COPY --chown=appuser:appuser src/ .
```

### 3. Запуск приложения от пользователя root

**Как в плохом:**  
Отсутствует создание пользователя и всё выполняется из под root.  
Если приложение взломают, злоумышленник получит права root внутри контейнера.

**Как исправлено в хорошем:**  
Создаётся пользователь `appuser` и контейнер запускается из под него.
```dockerfile
RUN adduser -D appuser
...
RUN mkdir -p /home/appuser/src/data && chown appuser:appuser /home/appuser/src/data
USER appuser
```

## Плохие практики использования этого контейнера

### 1. Запуск без флага `-v` (анонимный том)
Пока мы не удаляем контейнер или не перебилживаем образ данные в нём в volume будут одни и те же. Как тольао контейнер будет удалён, docker при следующем запуске нового контейнера создаст новый том со случайным именем-хешем, который будет пустым.  
При этом все предыдущие тома (ранее созданные для удалённых контейнеров) будут копиться (не удаляться) и забивать диск.
```bash
docker run app_good
```

**Как правильно:**  
В таком варианте запуска контейнера у тома всегда будет фиксированное название `app_data`, данные при удалениях контейнеров не будут пропадать. Диск не будет забиваться лишними томами.
```bash
docker run -v app_data:/home/appuser/src/data app_good
```

### 2. Запуск с переданными через флаг `-e` переменных окружения
Если передавать критически-важные переменные через флаг `-e` (например, креды для подключения к БД), то при запуске `docker inspect <имя_контейнера>` их можно увидеть в открытом виде - это небезопасно.
```bash
docker run -e USERNAME="admin" -e PASSWORD="123456" app_good
```

**Как правильно:**  
Безопаснее использовать менеджеры сикретов и внутри приложения обращаться за критическими кредами туда. 

## Когда не стоит использовать контейнеры

### 1. Legacy-монолит, завязанный на окружение хоста
Попытка загнать старое монолитное приложение в контейнер без переработки архитектуры часто приводит к огромным временным затратам, проблемам с логами, файловой системой и перезапусками, не давая при этом никаких плюсов.

### 2. Простые или одноразовые скрипты. 

Если мы делаем небольшой скрипт или только начинаем разработку проекта, развертывание через Dockerfile, сборка и настройка сетей могут создать избыточный порог входа и замедлить работу.
